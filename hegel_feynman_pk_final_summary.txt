我让 Hegel 和 Feynman PK 了一轮，又让他们互相批评后收敛。最终结论：

**最推荐的新方向**
不要再主打“压缩 vs 不压缩”，换成：

> **Evidence-Aware Adaptive Retrieval for SimpleMem**
> 面向 LoCoMo 的 SimpleMem 证据感知检索与轻量问题类型路由

核心 insight 是：

> LoCoMo 上性能瓶颈可能不是 memory 形态，而是“正确证据有没有进入最终 prompt”。

你本地 `locomo10.json` 是 10 个 conversations，但有 **1986 个 QA**。所以一个 full run 很慢是合理的。

**算法怎么做**
不要用 gold category 或 gold evidence 参与检索，避免测试集泄漏。只用问题文本做轻量判断：

- temporal：when / before / after / first / last / date
- entity-heavy：人名、地点、职业、关系
- multi-hop：多个实体、事件链
- unanswerable 风险：问题找不到强证据时允许“不知道”

检索排序可以做：

```text
score = semantic_score
      + bm25_score
      + entity_overlap
      + temporal_match
      - redundancy_penalty
```

再加两个东西：

- **MMR / context packing**：固定 token 或 memory 条数预算，不是无脑加 top-k。
- **uncertainty gating**：只允许一次扩大检索或 rerank，比如 top1/top2 分差小、实体覆盖不足、时间问题没检到时间信息。

**10 天内跑多少实验**
理论上你一天 3-4 个 full run，10 天是 30-40 个。但不要这么排。现实目标是：

- `8-12` 个可信 full run
- `20+` 个 retrieval-only pilot
- `5-10` 个 smoke/debug run
- 最后 2 天冻结代码、补结果、写分析

最小必跑 full 矩阵：

1. `SimpleMem original`：主 baseline，1-2 次
2. `SimpleMem larger top-k`：证明提升不是因为塞更多上下文，1 次
3. `SimpleMem + rerank`：BM25/entity/time/semantic 融合，1-2 次
4. `+ MMR/context packing`：固定预算下选证据，1-2 次
5. `+ query-feature routing`：轻量问题类型路由，1-2 次
6. `+ uncertainty gating`：最终方法，2 次左右

如果时间紧，砍到 6-8 个 full run 也可以，但必须保留：原版、larger top-k、rerank、final。

**最快 10 天能做到什么**
最快能做到一个可信毕业论文级结果：

> 在 SimpleMem + LoCoMo10 的统一协议下，证明证据感知 rerank / routing 能在相近上下文预算下提高 evidence recall，并观察它是否带来 F1 提升。

重点指标：

- Answer F1 / ROUGE-L
- evidence recall@5/10/20
- per-category F1
- avg retrieved memories
- avg context budget
- retrieval latency
- fallback/gating rate
- 失败案例分类

**不需要复现所有对比论文**
不需要，也不应该。

HingeMem、SmartSearch、D-Mem、MemMachine 这些可以放 related work，数字只写“作者报告”。你的主实验只需要在同一仓库、同一模型、同一数据、同一评测脚本下比较：

- SimpleMem original
- larger top-k
- semantic/BM25/entity/time rerank
- final method

你的 claim 不应该是“打败全领域 SOTA”，而应该是：

> 本文在统一 SimpleMem-LoCoMo 协议下，验证问题类型感知的证据检索和上下文编排能否提升长期对话问答的证据命中率与回答质量。
